# Workbench: a local web UI for the scripts

Status: built 2026-10-19 on branch `workbench` (milestones 1-7). Changes from
the plan below: backups don't close or reopen Anki (AnkiConnect's guiExitAnki
didn't close the launcher-based Anki, and the user prefers to do it by hand),
so Back up only runs backup-collection.sh while Anki is closed; the Example
sentences dry run previews write-sentences.rb on the existing YAML; both open
questions are settled (per-deck options are remembered; backups as above).

## Goal

A small local web app that runs this repo's scripts against one Anki deck at a
time, so the user can click through the workflow instead of typing commands. It
is a **script runner**, not a new application: the CLI scripts stay the source
of truth, and the Workbench only builds their command lines, runs them, and
shows their output plus a per-deck "what still needs work" view.

Mock-up (interactive, sample data, simulated runs):
https://claude.ai/artifact/CQXjoPnThq1Ur9sWAvJHoY. It is a guide to layout and
behavior, not a spec to copy pixel for pixel.

## Decisions already made (don't relitigate)

- **Sinatra.** The user knows it a little and may read the code. Keep it
  idiomatic and small; no frontend build step.
- **One deck per run.** Every deck-changing script requires `--target-deck`
  (see `lib/script_cli.rb`). The UI always has exactly one deck selected; there
  is no "all decks" mode.
- **Suggest the order, never enforce it.** Steps are listed in the suggested
  order with a "Suggested next" marker; any step can run at any time. When a
  step runs before something it depends on, show a non-blocking note (e.g.
  "Example sentences: 41 cards still need one; they'll be picked up later").
- **Claude is the default LLM provider**; OpenCode is offered for large
  batches. Providers, models and per-task defaults come from
  `config/llm-models.yaml` (`lib/llm_config.rb`). Model fields are dropdowns
  from that file, with the task default marked.
- **No VOICEVOX step.** Gemini audio appears as "Generate audio" in the main
  step list (no separate Audio section). VOICEVOX stays a CLI fallback that
  `generate-gemini-audio.rb` calls itself.
- **Pitch accent gaps are fine** (80–90% coverage is plenty). Words Wadoku
  can't cover are tagged `pitch-accent::unavailable` and don't count as missing.
- **Personal data stays out of git.** Never commit `config/deck-readings.yaml`,
  `prompts/translation/*` (except the とらドラ！ example), `prompts/local/`, or
  anything under `data/`, `temp/`, `backups/`.

## What already exists (built in the 2026-10-19 consistency pass)

- `lib/script_cli.rb` — shared flags and checks. Every deck script takes
  `-d/--target-deck` (required), and most take `--dry-run`, `--limit N`,
  `--force`, `--provider`, `-m/--model`. Exit statuses everywhere:
  **0** done, **1** something failed, **2** bad options, **3** stopped by a rate
  or usage limit (re-run the same command later to resume).
- `lib/deck_status.rb` — one predicate per workflow step (`needs_sentence?`,
  `needs_furigana_review?`, ...). Scripts select their notes with these, so the
  counts match what a run will process.
- `deck-status.rb --json [--target-deck DECK]` — per-deck counts:
  `{ "checks": [{key, label, script}], "decks": [{name, total, counts: {key: n}}] }`.
  The whole collection takes about 5 s; one deck is faster.
- `pull-from-takoboto.rb --cleanup t|s|b|x` answers its clean-up prompt, so no
  script needs stdin.
- `extract-words.rb` writes `metadata.target_deck` into its YAML;
  `write-sentences.rb --target-deck` refuses files or notes from another deck.
- Tests: `bundle exec rake test` (minitest, `test/`).

Run `./<script> -h` for the authoritative flag list before building each form.

## Architecture

```
workbench.rb              # entry point: parses --port, starts the app, opens the browser
workbench/
  app.rb                  # Sinatra::Base subclass: routes only
  steps.rb                # the step registry (table above) as Ruby data
  command.rb              # builds argv arrays from a step + submitted options
  runner.rb               # runs one script at a time, buffers output, tracks status
  views/index.erb         # the page
  public/workbench.js     # vanilla JS: forms, EventSource for output
  public/workbench.css
test/workbench/           # rack-test + unit tests for command.rb and runner.rb
```

- **Gems** (Gemfile group `:workbench`): `sinatra`, `puma`, `rackup`;
  `rack-test` in `:test`. Keep `bundle exec rake test` covering everything.
- **Start-up:** `./workbench.rb [--port 4567]` binds **127.0.0.1 only**, then
  opens the page (`open` on macOS, `xdg-open` elsewhere, or print the URL).
  Use Sinatra's host authorization (`set :host_authorization, permitted_hosts:
  ['localhost', '127.0.0.1']`) so another site can't drive it via DNS
  rebinding. Leave Rack::Protection's defaults on.
- **Never build shell strings.** `command.rb` turns a step + options into an
  argv array (`[RbConfig.ruby, script, '--target-deck', deck, ...]`) and the
  runner calls `Process.spawn`/`Open3.popen2e` with that array. Validate every
  value: deck must be in the deck list, flags must be in the step's registry
  entry, numbers must be integers, files must be inside the repo's `temp/` or
  `prompts/`. The same builder produces the command preview shown in the UI,
  so preview and execution can't diverge.
- **One run at a time.** The runner holds a mutex; a second Run while one is
  active gets HTTP 409 and the UI disables Run buttons. Keep each run's output
  in memory (and append it to `temp/workbench.log`).
- **Streaming output:** `GET /runs/:id/events` as Server-Sent Events (Sinatra
  `stream`), one event per output line, then a final event with the exit
  status. The scripts set `$stdout.sync = true` (in `lib/script_cli.rb`), so
  output arrives line by line through a pipe; merge stderr into the same stream
  (`Open3.popen2e`).
- **Cancel:** `POST /runs/:id/cancel` sends SIGINT. The scripts are
  resumable (pending tags, incremental YAML), so this is safe.
- **Environment:** pass the server's environment through
  (`ANKICONNECT_API_KEY`, `GEMINI_API_KEY`, `WHISPER_MODEL`, `VOICEVOX_URL`).
- **Exit statuses in the UI:** 0 → success; 1 → failed (show the tail of the
  output); 2 → a Workbench bug (it built bad options): show it loudly;
  3 → "Stopped by a usage or rate limit; run again later to resume", with a
  Run-again button.

### Routes

| Route | Does |
|---|---|
| `GET /` | The page. |
| `GET /api/decks` | Runs `deck-status.rb --json` (cache ~30 s; refresh after every run that changes the deck). |
| `GET /api/decks/:name` | `deck-status.rb --json --target-deck NAME` for a quick refresh. |
| `GET /api/config` | Steps registry, `config/llm-models.yaml`, prompt files, `temp/*.yaml`, Takoboto source decks, whether `prompts/translation/<deck>.md` exists. |
| `POST /api/preview` | `{step, deck, options}` → the argv (for display). |
| `POST /api/runs` | `{step, deck, options, dry_run}` → starts a run, returns `{id}`. |
| `GET /runs/:id/events` | SSE output stream. |
| `POST /runs/:id/cancel` | SIGINT the run. |
| `POST /api/backup` | See Backups below. |

Takoboto source decks: add a tiny read-only query (decks containing
`note:jp.takoboto`, with counts) either to `deck-status.rb --json` or as
`lib/` code the app calls. Prefer extending `deck-status.rb` so the CLI stays
the source of truth.

## The page

Follow the mock's layout:

- **Header:** deck selector, AnkiConnect status, last backup time + Back up.
- **Left:** step list grouped "Get words in" (Mined cards, Takoboto, Word list;
  no order) and "Fill in cards" (numbered, "Suggested order. Any step can run
  any time."). Badges: `N missing` / `Complete` / `Optional`; the first step
  with work left gets "Suggested next".
- **Centre:** selected step's description, options form, live command
  preview, Run / Dry run, out-of-order note, backup reminder for bulk steps,
  then the output log.
- **Right:** "Decks" list (every deck with how many cards need work; click to
  select), the selected deck's per-step completeness bars (clicking "N
  missing" opens that step), and an Advice list generated from the counts
  (e.g. "41 cards have no example sentence. Generate them first...").

**Example sentences** is the one multi-script step: run `extract-words.rb`,
then `generate-sentences.rb`; if "pause to review" is on, stop and show the
path of `temp/example-sentences.yaml` with a "Write N sentences to Anki"
button that runs `write-sentences.rb`. Otherwise run all three in sequence,
stopping at the first non-zero exit.

## Backups

`backup-collection.sh` needs Anki closed. On macOS the server can do
`osascript -e 'quit app "Anki"'`, wait for the process to exit, run the
script, then `open -a Anki` and wait for AnkiConnect to answer. Elsewhere, show
instructions instead. Record the last backup time (the newest file in
`backups/`) for the header. Before any bulk step, if the last backup is older
than a day, show a reminder with a Back up button; never block the run.

## Testing and safety

- Back up the collection before the first real (non-dry-run) run from the
  Workbench (`./backup-collection.sh`, Anki closed).
- Use `--dry-run` runs against a real deck for manual testing; the user's
  decks include とらドラ！, 呪術廻戦, 幽霊, 変な家 and others (see
  `./deck-status.rb`).
- rack-test the routes with the runner stubbed; never let tests spawn real
  scripts against Anki.
- Don't add features that modify cards outside the scripts: every card change
  must go through a script.
